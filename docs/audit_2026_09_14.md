## 2. HIGH — the CoT arm's headline number is a token-budget artifact

Both CoT runners used `--max-new-tokens 256`. That is not enough for the
reasoning the prompt requests, and the scoring depends on an `ANSWER:` line
that a truncated generation never reaches.

| arm | reached `ANSWER:` | truncated | accuracy on truncated |
|---|---|---|---|
| llama · TIME | 77.9% | **22.1%** (23,152) | **0.08%** |
| mistral · TIME | 87.2% | 12.8% (13,414) | 0.11% |
| llama · TimeBench | 92.5% | 7.5% (1,574) | 0.70% |
| mistral · TimeBench | 86.9% | 13.1% (2,751) | 0.00% |

Truncated outputs stop mid-sentence mid-reasoning — they are budget losses, not
reasoning failures. The effect on the headline is large and it **reverses the
sign of the result on TIME**:

| | as scored | conditional on reaching the anchor | standard zero-shot |
|---|---|---|---|
| llama · TIME | 38.52% *(−2.94 vs baseline)* | **49.41%** *(+7.95)* | 41.46% |
| llama · TimeBench | 49.11% *(+3.93)* | **53.01%** *(+7.83)* | 45.18% |
| mistral · TIME | 33.65% | 38.56% | — |
| mistral · TimeBench | 36.08% | 41.49% | — |

Read as scored, CoT *hurts* on TIME. It does not — 22% of the runs simply ran
out of tokens.

**The conditional column is an upper bound, not a point estimate.** Items that
need more reasoning are plausibly harder, so the true value lies between the two
columns. Only a re-run settles it.

**Fixed:** both runners now use `--max-new-tokens 768`, with the measurement
recorded in the script header. The zero-shot CoT results need re-running to be
quotable; the few-shot arm has not run yet and will not inherit the defect.

**Also fixed:** `rescore_v5_protocol.py` now reports `anchor_missing_pct` for
any anchor-style arm and prints a warning line, so this class of defect cannot
hide in a future CoT run.

### Side note: `strict_pct` does not mean the same thing for a CoT arm

The strict first-line metric reads ~0.0% for every CoT arm, because the first
line of a CoT output is "Step 1: …" by construction. That is not evidence of
scorer dependence the way it is for a fine-tuned arm — the `ANSWER:` anchor is
the *designed* extraction point and was specified in the prompt in advance.
Do not compare `strict_pct` across prompting styles.

## 3. HIGH (methodology) — the CoT arm changes three things at once

The zero-shot CoT arm differs from the standard zero-shot baseline in **three**
ways simultaneously:

| | standard zero-shot | zero-shot CoT |
|---|---|---|
| system prompt | **none** | `COT_SYSTEM_PROMPT` ("expert temporal-reasoning teacher…") |
| answer instruction | "return only the final answer" | "Step 1… / finish with `ANSWER:`" |
| `max_new_tokens` | 128 | 256 (now 768) |

So "CoT is worth +7.95pp" is really "a persona system prompt **plus** a
step-by-step instruction **plus** 2–6× the token budget is worth +7.95pp". The
effect cannot be attributed to chain-of-thought.

This is the **same mistake as v7** — six bundled changes whose regression took
two further arms (v7c, v6d) to attribute — and the same discipline that D57
imposed on the training arms should apply to the prompting arms. Two cheap runs
would attribute it:

1. standard prompt + `COT_SYSTEM_PROMPT` + 128 tokens → isolates the persona;
2. standard prompt + no system prompt + 768 tokens → isolates the budget.

Each is one evaluation leg. Without them the CoT result is a bundled arm and
must be reported as one.

## 4. HIGH — a queued script reintroduced a retired hazard

`scripts/run_zs_tram_llama.sh` (gated to fire automatically when the few-shot
chain finishes) ran:

```
run_baselines.py --benchmark tram --results-dir ./results/baseline/zero_shot_v3
```

`run_baselines.py` is the **HF** engine; that directory is the **vLLM** TRAM
baseline every TRAM arm is compared against. This is defect **H4** from the
2026-09-09 audit verbatim — it is precisely why
`scripts/retired/run_zeroshot_tram.sh` was retired on that date.

It is also **redundant and aimed at stale data**: the zero-shot TRAM baseline
was re-run on corrected prompts on 2026-09-13 and lives at
`results/tram_fixed/zero_shot/` (46.95%), while the path this targeted holds
the superseded broken-prompt predictions (35.20%).

Realistic damage was bounded — all 980,918 ids are already present, so it would
have no-opped, reported `OK`, and refreshed reports from stale predictions
rather than corrupting the file. But the resume file carries no engine tag
(written before 2026-09-09), so the 2026-09-12 resume guard would only *warn*.

**Fixed:** the script now refuses to run and explains why. It was replaced via
a new inode so that any shell executing the old copy could not read the
replacement mid-stream. (No such shell existed — an earlier claim in this
session that a waiting process was alive was a `pgrep -f` self-match, corrected
on the spot.)

## 5. MEDIUM — the CoT arm was invisible to the canonical scorer

The CoT predictions have existed and been complete since 2026-09-09, and
`scripts/rescore_v5_protocol.py`'s `ARMS` had **no entry for them**. They
therefore never appeared in the canonical table; the only numbers recorded were
the per-run `zero_shot_report.json` files, which come from the live harness, not
the frozen scorer.

This is the same defect class as **F1** on 2026-09-09 (v7-corrected missing from
`ARMS`, which would have silently omitted the arm the campaign existed to
produce). It is a recurring failure mode of a hand-maintained arm list.

**Fixed:** `zsCoT-llama`, `zsCoT-mistr`, `fsCoT-llama` and `fsCoT-mistr` are now
in `ARMS` for TIME and TimeBench. Missing files report as missing and are
skipped, so the few-shot entries are safe to carry before that run exists.

**Structural recommendation:** the arm list should be discovered from the
results tree and checked against a manifest, not hand-edited. This is the third
time an arm has been missing from it.

## 6. What the CoT result actually says, stated carefully

Taking the bundled arm as it is, and using the conditional-on-anchor figures as
an upper bound:

- **On TimeBench, base-model CoT beats every fine-tuned arm in the project.**
  49.11% as scored — already above v3-corrected's 48.46%, the previous record —
  and 53.01% conditional on completing. With **no training at all**.
- **On TIME it is ambiguous** until the re-run: 38.52% as scored (below the
  41.46% baseline) versus 49.41% conditional (well above it).
- **Mistral is worse than llama on both**, consistent with its exclusion from
  the vLLM path for parity reasons (D46/D53).

If the re-run confirms even half the conditional gain, the thesis has a second
substantive result to sit beside the gold-context/retrieved-context split
(§0a-bis of the 2026-09-12 audit): **prompting the base model outperforms every
fine-tune this project produced, on two of three benchmarks.** That is a
strong, cheap, and honest finding — and it makes the campaign's negative result
about fine-tuning more interesting, not less.

## 6b. Three further defects, found by making §5's recommendation real

`ARMS` is now **checked against the results tree** (`unlisted_arms()`): the
list stays hand-written, because it encodes which directory is canonical for an
arm and that cannot be inferred, but any complete predictions file it does not
mention is now reported instead of being invisible. `_NOT_ARMS` carries an
explicit reason for every deliberate exclusion.

It immediately found more:

1. **A fourth missing arm.** `results/baseline/zero_shot_v3/mistral/` is
   complete on TIME (104,951 rows) and TimeBench (21,188), is **quoted in
   `session_state.md`**, and had never been scored by the frozen scorer. Under
   the frozen protocol: **TIME 37.26%** (quoted 36.17) and **TimeBench 45.54%**
   (quoted 44.90) — the same live-harness-vs-frozen mismatch as §5. Now in
   `ARMS`. Mistral stays a side experiment (banned from vLLM for a 2.20pp
   parity failure, D46/D53) and is not comparable to the llama campaign; it
   should simply be scored by the same scorer as everything else.

2. **The mistral TIME leg has a torn line** (`TIME_Newest.json-4540`): 104,950
   unique ids + 1 torn = 104,951 raw lines, 104,938 scoreable against 104,939
   expected. The old rule called that `PARTIAL` and dropped a 99.999%-complete
   arm from the table entirely. **`PARTIAL` exists to reject an ABORTED leg** —
   a biased prefix, length-sorted on HF or category-blocked on vLLM — which is
   not the same thing as a complete run that lost one scattered line to a torn
   write. The rescore now distinguishes them: when `n + torn >= expected` the
   run covered the benchmark, so it is scored with a visible note.

3. **The frozen-era results are now explicitly excluded, with a reason.**
   `results/finetuned{,_v2,_v3,_v3_vllm}/` hold 106,500-row TIME runs from the
   original broken harness, superseded in full by `results/corrected/`. They
   are kept for the three-stage comparison in `docs/mistake_ledger.md` and are
   named in `_NOT_ARMS` so nobody wires them in by accident.
