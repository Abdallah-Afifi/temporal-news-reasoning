# Audit 2026-10-04 — full project review (v11 → v13, Mistral, CoT, repo)

Read-only audit across five areas run in parallel, with the most serious
findings re-verified directly before being written here. Nothing was
modified during the audit except the corrections to today's own write-up
listed in §8. The Mistral s44 training run was not touched.

Severity: CRITICAL = changes what can be claimed; HIGH = must fix before the
next run / quote; MEDIUM = should fix; LOW = note.

---

## 1. Data provenance

**1.1 CRITICAL — the v13 "GLM-5.2 wave" (AUG_GLM3, 4,519 rows) was not
written by GLM chat; it was produced by Python template generators.**
`scripts/glm_v13_build/README.md` states it outright: `gen_reasoning.py`
(packets 042–102), `gen_dialogue.py` (033–035), `gen_stories.py` (037–039,
"15-template scenario bank, slot-filled endings"), `gen_rel.py` (003–006);
the remaining packets were assembled by `build_*.py` / `*_lib.py` builders
from string-literal passages (`parts/`). Verified directly:
- 61 of 109 replies in `data/glm_raw_v13/` share one mtime second
  (2026-10-04 14:23:47).
- Every one of the 4,519 rows carries `source_dataset: "AUG_GLM2"` — labelled
  as the GLM-authored corpus, not AUG_GLM3 and not programmatic.
- `run_v13_glm.py` (the API route) was never run; no GLM API log exists.

The author was the GLM-backed coding agent (the `opencode` session referenced
in `session_handoff.md`), but it wrote *programs* that template the data,
not per-packet LLM completions as `v13_glm_runbook.md` specifies.
`v13_plan.md`'s premise — LLM-diverse language for the language-heavy weak
categories — is not met, and this is an **unrecorded deviation** from the
pre-registration. v13 as built is effectively "v12 + two programmatic
corpora".

**1.2 HIGH — part of the v11/v12 AUG_GLM2 corpus was built the same way.**
The same builder libraries (`er_lib.py:14`, `nli_m_lib.py:14`,
`syn_gen.py:10`, `td_lib.py`, `st_lib.py`, `dc2_lib.py`, `lf_oc_lib.py`)
write to `data/glm_raw/{fno}.txt` — the v9–v12 corpus directory. Files
271–313 were written 2026-09-23 10:14–14:15 in same-second bursts; they hold
**800 of 5,298 ingested AUG_GLM2 rows (15.1%)**, and `combined_80_20_v11`
was built later that day (15:27), so they are in v11's and v12's training
data. The builders also reference earlier file numbers (108–269), so the
script-built share may be larger; files 1–270 were not individually traced.
*v11's measured gains are unaffected* (they are measured on test, whatever
the data's origin), but every description of AUG_GLM2 as "GLM-authored"
(`README.md`, `results_and_methodology.md` §10.1, v9-glm docs) is inaccurate
for at least 15% of it.

**1.3 MEDIUM — 807 of the newest CoT traces (files 103–197) were written by
the coding agent, not GLM chat** as `cot_generation_protocol.md` specifies.
`scripts/glm_v13_build/cot_evidence.py` selects evidence sentences by
scoring +3 per gold token — i.e. the evidence step is chosen knowing the
answer. Style shift early→late: 801/807 late traces are exactly 2 steps;
gold verbatim in Step 1 in 92% (vs 37% early). Answers are correct and
grounded; the traces are just thinner and more formulaic. (The CoT bank also
kept growing during the audit: 1,900 keyed / 1,693 banked / 207 documented
skips at audit time — accounting exact.)

## 2. Data quality

**2.1 HIGH — storytelling (AUG_GLM3) has a length shortcut.** In 334/401
rows (83%) the gold is the longer ending; 111 distinct ending skeletons for
802 endings; distractors are absurd. This is the category aimed at v11's
TRAM storytelling regression, and it teaches "pick the longer ending".

**2.2 MEDIUM — relation label noise in packets 001/002**: 8 of 28 dated
pairs reversed (~29% on that subset). Script-built `relation_batch03`:
89/89 consistent.

**2.3 MEDIUM — duration rows are trivial**: 122/250 rows offer four options
with the same number and only the unit changing; 99 use the broken template
"How long did it take the X to take/last?".

**2.4 MEDIUM — extract teaches substring matching**: the gate requires
correct options to appear verbatim in context, while TIME Extract includes
indirect mentions; none exist in training.

**2.5 MEDIUM — AUG_PROG timeline: 227/2,000 rows (11.4%) under-determined**
(same-year facts ordered by hidden day-level dates). `verify_timeline`
recomputes the gold from those same hidden dates, so it is not independent;
the generator docstring's "every gold re-derived by independent verifiers"
overstates it. 412 `prog_duration_compare` rows have incoherent text.

**2.6 MEDIUM — ~11% of TimeQA training golds appear wrong.** CoT generation
skipped 207/1,900 sampled TimeQA rows as contradicted/unsupported; three
spot-checked are genuinely wrong (g0941, g0012, g0069). All remain in
`combined_80_20_v12` and therefore in v13.

**2.7 HIGH — ingest gate acceptance is meaningless for script-built data.**
`gen_reasoning.py:483`, `gen_dialogue.py:149`, `gen_stories.py:147` call
`ingest_glm_batch.check()` and only emit rows that pass; the ~99–100%
accept rate is by construction. Similarly the CoT gate docs claim Step 1
must not contain the gold; the code (`ingest_cot_batch.py:111–119`) only
rejects a giveaway phrase.

**Clean:** mechanically checkable golds are correct (Order_Compare 175/175,
Relative_Reasoning 325/325, ordering 124/124, AUG_PROG 75/75 recomputed
independently); no exact duplicates; MCQ letter balance fine; **no benchmark
contamination** (project's own shingle filter: 0/4,519 AUG_GLM3 rows; one
AUG_PROG TRAM-arithmetic match correctly dropped).

## 3. The v13-prog pilot (+11.26pp dev objective)

**3.1 HIGH (interpretation) — the TimeBench gain is one subset copying the
benchmark's own template.** Dev by subset (zs → t09 → pilot):
`date_arith` 5.27 → 11.60 → **100.00** (n=474); tracie 49.0→56.8→60.3;
mctaco 85.3→85.3→94.7; tempreason 54.7→64.6→59.2; timedial 74.4→64.0→59.3;
timeqa 43.8→55.2→52.4. `date_arith` alone is ~+17–18 of the +21.36pp;
without it the rest gains ~+3.4pp, *below* t09. `prog_arith_month` reproduces
TimeBench's question template verbatim, including its ungrammatical wording
(`generate_v13_prog_data.py:207–236`); zero item overlap, so it is task
learning, not leakage — but `date_arith` is ~19% of TimeBench
test-minus-dev. **Any v13 TimeBench number must be reported with and without
`date_arith`.** Same pattern smaller: TIME Computation (generator copies
TIME's Hint text), TIME Extract, TRAM arithmetic. Pilot losses vs zero-shot:
TIME Order_Compare −19.7, timedial −15.1.

**3.2 MEDIUM — the pilot's control is confounded.** `score_v13_pilot.py`
compares to t09 (v11 data); the pilot's data is v12 + AUG_PROG, so
pilot − t09 mixes the v12 card fixes with AUG_PROG.

## 4. Code

Tests: 242 passed, 6 skipped (JVM-only RAG tests). LLaMA/Mistral training
paths verified identical in the parts that matter (parity tokenization,
`seed=`, answer-only loss mask, gold-truncation drop, external selection);
schedules use the pinned date for LLaMA / none for Mistral,
`--system-prompt none`, and results dirs match the rescorer — clean.

**4.1 HIGH — `scripts/lora_soup.py:68–80` averages A and B separately.**
The merged update becomes (1/3ΣB)(1/3ΣA) = 1/9 ΣᵢΣⱼ BᵢAⱼ: each seed's own
term weighted 1/9, plus cross terms between independently initialised A's
(≈ noise). `checkpoints/llama_v11_soup/final` is built this way and
`run_schedule_v13.sh` would evaluate it. Fix: average the merged deltas
ΔWᵢ = (α/r)BᵢAᵢ per module (merge into the base, or SVD back to a LoRA).

**4.2 MEDIUM — rebuilding `combined_80_20_v13` overwrites the pilot's data**
in place (all v13 configs and the pilot read the same directory). Copy it
first (e.g. `data/training_versions/v13_provisional/`).

**4.3 MEDIUM — drivers mark completion on failure, and nothing guards the
GPU.** `run_v13_prog_pilot.sh` writes its completion marker even when eval
or scoring fails (how today's score crash released the GPU);
`run_schedule_v13.sh` ignores `run_arm` failures and does not check whether
`run_mistral_seeds.sh` is still running — launching it now would put two
jobs on one GPU.

**4.4 MEDIUM — Mistral is trained in 4-bit QLoRA but evaluated merged into
the fp16 base.** Consistent across HPO, m05, s43, s44 and the fp16
zero-shot, so the deltas are valid, but they measure "fp16 base + QLoRA
adapter"; undocumented until now (added to §12.4).

**4.5 LOW–MEDIUM — the rescorer pairs every arm against one global
reference** (`rescore_v5_protocol.py:720`), in the printed table *and* in
each saved `_paired`. `results/rescored/mistral_test_minus_dev.json` (rewritten
2026-10-04 22:25) therefore holds every LLaMA arm paired against
*Mistral's* zero-shot — read only Mistral arms from it. A missing reference
silently falls back to the legacy HF `zero-shot` arm. McNemar sign
convention is consistent and matches published z.

**4.6 LOW** — `results/hpo_v13_pilot/` missing from `_NOT_ARMS`;
`push_to_second_pc.sh` excludes `results/` unanchored and has no
`--update` (a newer remote file would be overwritten).

## 5. Results integrity

**Clean.** 30 prediction files (10 arms × 3 benchmarks): no malformed lines,
NULs, duplicate or missing ids; identical id sets across arms (pairing
valid); no new torn lines / bit flips. Dev ids are genuinely excluded
(n = 99,939 / 18,575 / 970,918 everywhere; files hold dev+test, e.g. TRAM
980,918 = 970,918 + 10,000). Every number written into
`results_and_methodology.md` §11–12 and `README.md` today matches the JSON.

**5.1 HIGH — the v12 verdict written today (§11.2) was biased against the
v12 arms.** The control "v11-best" is the seed-42 adapter = the HPO winner
reused, and the best of the three v11 seeds on TIME and TRAM (selection
bias). Re-measured against the v11 three-seed mean (46.42 / 46.30 / 53.10),
with noise for single-run-vs-mean ≈ sd·√(4/3) (0.50 / 0.45 / 0.79pp):

| Arm vs control | TIME | TimeBench | TRAM |
|---|---|---|---|
| v11-2ep vs v11 mean | −0.30 (noise) | **+2.97** | **+2.29** |
| v12-data vs v11 mean | −0.11 (noise) | +0.63 (marginal) | +0.95 (marginal) |
| v12-ctx vs v12-data (noise √2·sd: 0.61/0.55/0.96) | −0.27 (noise) | +0.84 (marginal) | +0.12 (noise) |

So **v11-2ep is a clean win** (real gains on TimeBench/TRAM, TIME neutral) —
not "mixed" as written this afternoon; the "real TIME loss" came from
comparing against a lucky seed. Corrected in §11.2 (see §8).
