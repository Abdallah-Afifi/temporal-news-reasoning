# Audit — 2026-09-14 (second pass, evening)

Triggered by a request to audit the whole project while a few-shot CoT
evaluation was running. The run was stopped. Method as before: every claim
recomputed from the artefacts in this checkout, nothing taken from a prior
document on trust.

Test suite: **143 passed, 6 skipped, 0 failed**, before and after every change.

---

## Summary

The few-shot CoT arm — three completed/partial legs, ~26 GPU-hours — is
**void**. Not degraded: void. The worked examples it exists to test were
deleted by the tokenizer before the model ever saw them, on 100% of items, on
both benchmarks. So was the system prompt. Nothing downstream could detect
this, because a left-truncated prompt is not an error — it is just a shorter
prompt.

Four defects, in descending order of consequence:

| # | severity | defect |
|---|---|---|
| 1 | **CRITICAL** | The 9,393-token exemplar preamble is left-truncated away at the 4,096-token inference limit. The arm was never few-shot. |
| 2 | **HIGH** | The running leg used `--max-new-tokens 256` after the script had been fixed to 768 — a stale process carrying a retired budget. |
| 3 | **HIGH** | `.done` markers are budget-blind, so a corrected relaunch would have *skipped* the legs that needed redoing. |
| 4 | **MEDIUM** | The resume guard checks model/adapter/engine but not prompt style or token budget — the two settings that decide what the model emits. |

Also recorded: a harness file was replaced mid-campaign with no version
control (§5), and the README documents a scorer invocation that yields stale
TRAM numbers (§6).

## 1. CRITICAL — the few-shot arm was never few-shot

`_build_cot_fewshot_prompt` (`scripts/run_baselines.py`) renders

```
Worked examples:\n\n <k blocks> \n\nNow solve this one, the same way.\n\n <target>
```

so the exemplars sit at the **front**. Inference tokenizes with
`max_length=4096` and `truncation_side="left"`
(`src/models/inference.py:67,150`) — over-length prompts lose their *beginning*.

The mined exemplar file rendered to **9,393 tokens**, against a 4,096 limit.
Per-exemplar cost, measured with the model's own tokenizer through the
runner's own renderer:

| exemplar | kind | context chars | tokens |
|---|---|---:|---:|
| 0 | ordering | 0 | 109 |
| 1 | duration_phrase | 1,629 | 539 |
| 2 | phrase_qa | **20,144** | **4,545** |
| 3 | phrase_qa | **17,936** | **4,183** |

Two exemplars carry ~38,000 characters of context between them and account for
93% of the preamble.

Consequences, measured on 3,000-item samples of each benchmark:

| | TimeBench | TIME |
|---|---|---|
| prompts exceeding the 4,096 limit | **100.00%** | **100.00%** |
| median target-block size | 132 tok | 1,542 tok |
| median preamble tokens **surviving** | 3,964 (42% of 9,393) | 2,554 (27%) |
| items retaining **zero** exemplar text | 0 | ~4% |

What the model actually received was the **tail** of the preamble: a fragment
of exemplar 3 beginning mid-context, mid-sentence, with no "Worked examples:"
header and no complete example anywhere in it. The nominal k=4 was, in
practice, a broken fraction of one.

**The same truncation deleted the persona.** `COT_SYSTEM_PROMPT` is the first
message in the chat template, so it sits in front of everything and was cut
from **every** few-shot item — while the zero-shot CoT arm, whose prompts are
far shorter, kept it. `run_fewshot_cot.sh`'s header claims "the ONLY delta is
the visible exemplars, so the fewshot-vs-zs-R comparison is clean". The actual
deltas were: fragmentary exemplars, **no system prompt**, a malformed chat
opening, and a different token budget. Nothing about that comparison was clean.

### Root cause

`mine_cot_exemplars.py` selected on

```python
sorted(..., key=lambda e: sum(len(s) for s in e["steps"]))
```

— the **reasoning trace only**. `context` is never measured. The declared rule
"shortest verified-correct trace wins" is sound for teaching termination, and
it was implemented faithfully; it simply has nothing to do with how much room
the exemplar occupies. A short trace attached to a 20,000-character context
sorts first.

### Why nothing caught it

The prompt is assembled as a string and only becomes over-length at
tokenization, inside the inference wrapper, where truncation is silent by
design. No assertion, log line or metric anywhere related prompt size to the
4,096 limit. The arm produced plausible accuracies (43.7% / 42.8%) and a
plausible truncation profile, and the 2026-09-14 audit reviewed
`_build_cot_prompt` for correctness — which it is. The defect lives in the
gap between a correct prompt builder and a correct tokenizer.

### Fixed

- **`mine_cot_exemplars.py`** now enforces a budget *at selection time*:
  `MAX_EXEMPLAR_TOKENS = 450`, `MAX_PREAMBLE_TOKENS = 1600`. Oversized
  candidates are dropped **before** generation (saving GPU); the exact size is
  re-checked after the trace exists; and the script **refuses to write** a set
  whose rendered preamble exceeds the cap. Sizes are measured with the model's
  tokenizer through `_format_cot_exemplar` — the runner's own renderer — so the
  miner and the runner cannot drift apart about what an exemplar costs.
- **`run_baselines.py::_load_cot_exemplars`** refuses an over-budget exemplar
  file, so a hand-edited or stale file cannot re-enter by the back door.
  Verified: it now rejects the offending file at ~10,371 estimated tokens.
- Budget arithmetic: 4,096 limit − ~90 (system prompt + chat scaffolding)
  − 1,600 (preamble) leaves ~2,400 tokens for the target block, comfortably
  past TIME's p90 of 2,135.

**Artefacts quarantined**, complete and unmodified, at
`results/baseline/few_shot_cot_SUPERSEDED_truncated_exemplars/` with a
`WHY_SUPERSEDED.md`; added to `_NOT_ARMS`. The exemplar file is renamed
`data/cot_fewshot_exemplars_mined.json.SUPERSEDED_9393_tokens` so the miner
re-mines rather than reusing it.

## 3. HIGH — `.done` markers would have skipped the legs that needed redoing

`logs/fewshot_cot/llama_timebench.done` and `mistral_timebench.done` both read
`OK`. `done_ok()` tested `= "OK"`. So a relaunch of the corrected script would
have **skipped both completed legs** and re-run only TIME, leaving the arm
permanently split across two token budgets — with no warning, because the
marker records no budget.

This is the same failure shape as §2: state that outlives the configuration
that produced it.

**Fixed** in `run_fewshot_cot.sh` and `run_zs_cot.sh`: the budget is declared
once as `MAXNEW` and stamped into the marker (`OK:768`); `done_ok()` requires
the stamp to match. A budget change now invalidates its own markers
automatically. The six existing `OK` markers are already correctly invalid
under the new rule — no manual deletion needed, which is the point.

## 4. MEDIUM — the resume guard ignored prompt style and token budget

`run_baselines.py` refuses to resume across a change of `model_dir`,
`adapter_dir` or `engine` (2026-09-09 M2 / 2026-09-12). It did **not** check
`prompt_style` or `max_new_tokens` — the two settings that decide what the
model actually emits. A 256-token prefix and a 768-token remainder would blend
into one arm silently, and nothing in the predictions file would record it.

**Fixed:** both are now recorded per row in `_RUN_PROVENANCE`, and the guard
compares them.

- `prompt_style` mismatch → **always fatal**; the rows on disk answered a
  different prompt.
- `max_new_tokens` mismatch → **fatal unless `--allow-budget-change`**. That
  flag exists for exactly one sound workflow: `salvage_cot_truncated.py` drops
  every row that ran out of budget, then the leg re-runs at the larger cap.
  Greedy decoding makes the kept rows byte-identical under a larger cap, so
  the blend is correct — but only when deliberate.

Verified by integration test: budget mismatch aborts without the flag;
proceeds with it; a prompt-style mismatch aborts even with it.

## 5. Recorded, not fixed — the harness has no version control

`scripts/run_baselines.py` was modified at **2026-09-13 18:53**, 55 minutes
into the `llama_timebench` leg (17:58–23:22). Python had already imported the
module, so that leg ran entirely on the old code — but the old code is
**unrecoverable**: the last commit touching the file is months old, every
recent change is uncommitted, and no copy on this machine is newer than
2026-05-11.

One difference is provable from the artefacts. That leg wrote **21,188** rows;
every leg after 18:53 writes **21,075**. The 113 extra are the blank-gold
TimeBench `timeqa` items (`reference == ['']`), which the post-18:53 loader
skips. All 113 score 0 by construction.

**No published number is affected.** `rescore_v5_protocol.py` drops blank-gold
rows for every arm alike, so all arms are scored on 21,075 regardless of what
their file contains. Verified across every TimeBench predictions file: 13 carry
the 113 rows (zero-shot, v1–v6, v7, both zsCoT legs), 3 do not (v6d, v7c,
fsCoT-mistral) — and the canonical table is consistent anyway.

But the episode means a campaign with a "frozen protocol" cannot say what code
produced any given number. **Recommendation: commit the harness.** Everything
else in this audit is a bug with a fix; this one is a standing risk that will
keep generating bugs of the kind in §2, §3 and §5 until the working tree is
under version control.

## A1. HIGH (scoring) — the content guard covered only bare years

`same_date` reduces both sides to a signature at the most specific level
available — `ymd`, else `ym`, else `y` — and requires the same level and the
same values. The 2026-09-07 audit added a content-substitution guard on top,
because a shared year alone was crediting answers that said the opposite of
the gold ("the 1979 establishment" vs "the 1979 overthrow").

**That guard was only ever applied to the `y` branch.** For `ym` and `ymd` the
function returned `True` on the strength of the shared date alone, with no
check on the surrounding words — and `_MAX_WORDS` allows up to 12 words a
side. So a shared date licensed any claim about it.

Measured on TIME, items credited **only** by date-equivalence where the
content words are substituted rather than merely dropped or added:

| arm | items | of n |
|---|---:|---|
| zero-shot | 27 | 0.026pp |
| v6-vllm | 26 | 0.025pp |
| v7c-vllm | 32 | 0.031pp |

Examples, all scored **correct** before this fix:

```
pred "Britain and Ireland suspended flights to Egypt on November 1, 2015"
gold "Russia and Britain suspended flights to Egypt on November 1, 2015."

pred "A third party mediated the talks between Israel and Hamas on July 8, 2017"
gold "Egypt mediated the talks between Israel and Hamas on July 8, 2017"

pred "Egyptian military operations in July 2015"
gold "Israeli airstrikes in July 2015"

pred "1 day after September 25, 2015."
gold "2 days after September 25, 2015"
```

The last one is a temporal-reasoning error scored as a temporal-reasoning
success, on the project's own subject matter.

**Fixed.** The same subset rule now applies at every level: date scaffolding
(month names, day numbers, ordinals, years) is set aside, so a genuine
reformatting still matches, and only substituted CONTENT words are refused.
Three regression tests pin it, including that the reformattings the module
exists to credit ("18 March 1934" ↔ "March 18, 1934", "1934-03-18",
"September 1183" ↔ "Sep, 1183") still pass and the level rule is unchanged.

**Impact on all 32 published cells**, re-scored before and after:

| benchmark | movement | rank changes |
|---|---|---|
| TIME | −0.01 to −0.04pp | none |
| TimeBench | **0.00pp (bit-identical)** | none |
| TRAM | −0.01 to −0.03pp | none |

The v6-vs-zero-shot TIME gap is 0.72pp before and after. §1's table carries
the corrected values; figures elsewhere in that document are within 0.04pp
and were deliberately not swept (see the note under §1).

## A2. LOW — ordinal days lose their day, and are left that way

Found while writing the A1 tests. `_DMY` requires a bare `\d{1,2}` for the
day, so "March 3rd, 2015" parses as month-year only and the level rule then
refuses it against the full-date gold "March 3, 2015" — exactly the defect
this module exists to remove.

Measured: **2 items on zero-shot, 3 on v6, 2 on v7c** (~0.002pp), an order of
magnitude below A1, near-uniform across arms, and a *loss* rather than an
over-credit. Widening the day pattern risks over-matching for no measurable
gain, so it is **pinned as a known limitation** in
`tests/test_date_equivalence.py` rather than fixed. Revisit if a future arm
emits ordinals at a materially higher rate.

## A3. Verified sound — contamination, statistics, exemplars

Re-derived from the artefacts, not carried over:

- **Train/benchmark contamination.** `docs/results_and_methodology.md` §4
  states that v1's pool contains 49 verbatim benchmark questions and that
  every builder from v2 carries a hard guard. Both check out exactly:
  `data/combined_80_20_split/` has **41 in train + 8 in val = 49**, and
  `data/combined_80_20_v6/` has **0** in either, against 75,857 unique
  normalized benchmark questions. The doc is accurate to the item, and it is
  already explicit that `results/overlap_audit_fullzip.json` (timeqa_easy
  8.6%, menatqa_scope 5.84%) is v1-era and does not describe v2+.
- **McNemar** is implemented correctly — `z = (c−b)/√(b+c)`, χ² with
  continuity correction — and the doc is right that the unpaired two-
  proportion z is the conservative one on this design. Both are reported.
- **Re-mined exemplars** (2026-09-14 23:24): preamble **437 tokens** against
  the 1,600 cap and the 4,096 limit, leaving 3,569 tokens of headroom — past
  TIME's p90 target block of 2,135. Four clean, short, correctly-reasoned,
  properly-terminated traces. **0 collisions** against 126,014 benchmark
  items. The arm will now actually be four-shot.
- **Greedy decoding needs no seed.** `run_baselines.py` sets none, but
  `temperature=0.0` / `do_sample=False` makes generation deterministic;
  training sets `set_seed(42)`.

### Observation, not a defect: the new exemplars carry no context

All four re-mined exemplars are self-contained questions with empty
`context`, whereas most benchmark items supply one. The worked examples
therefore demonstrate the output format and termination discipline — which is
what D59/D61 says they are for — but never demonstrate grounding an answer in
a provided passage.

This is strictly better than what it replaced (two of the old four carried
contexts, but those contexts were truncated away in full). It is worth a
deliberate decision rather than a default: if the arm should also demonstrate
context use, re-mine preferring candidates with a short non-empty context,
which the 450-token per-exemplar budget accommodates (~250 tokens of
context). Left as-is pending that call.
