# Audit 2026-09-23 — why no fine-tuned arm beat zero-shot, and the v11 fix

Scope: the whole evaluated chain — training pipeline, evaluation and scoring,
training-data construction — audited before a hyperparameter search, so the
search would not tune around defects. Three independent read-only audits
(training / eval+scoring / data), with every CRITICAL and MAJOR claim then
re-verified directly in code or data before any fix. Fixes are in the files
named; nothing here has been run on the GPU yet (this session has no GPU
access). Protocol for what follows: [`hpo_v11_protocol.md`](hpo_v11_protocol.md).

Status legend: **FIXED** (code/data changed, tested) · **DISCLOSED** (cannot
or should not be changed; stated in the write-up) · **OPEN**.

---

## 1. CRITICAL — trained on one prompt, evaluated on another · FIXED

Every arm v1 → v10-glm:

| | Training (`shared/prompt_templates.build_chat_messages`) | Evaluation (`run_baselines._build_zero_shot_prompt`) |
|---|---|---|
| system message | custom `TEMPORAL_SYSTEM_PROMPT` | none for zero-shot; the custom one for fine-tuned |
| instructions | none | "You are a temporal reasoning assistant." / "Answer the question using only the provided context…" / "Return only the final answer…" |
| MCQ options | left inside the question text | separate `Choices:` block + "Respond with the option text, or a single letter (A/B/C/D)." |
| NLI items | "Premise:/Hypothesis:" inside the question | NLI instruction + `Premise:\n{context}` + `Hypothesis: {question}` |

Verified by reading both builders (`prompt_templates.py:42`,
`run_baselines.py:101-136`). So every fine-tuned model was scored on a prompt
it never saw, while zero-shot got the instruction prompt it follows natively
— and the two arms also differed in system prompt. The eval audit found the
matching failure signature: in the regressing categories the fine-tuned model
answers off-list (TimeBench temporal_dialogue 78.7 → 48.6: zero-shot answers
"B.", fine-tuned answers "12 hours" when no option says so; TRAM storytelling
76.9 → 63.0, invented endings). The 2026-09-13 TRAM analysis had already
called the TRAM loss "a format effect" (`results_and_methodology.md` §9);
this is its mechanism.

**Consequence for every past number:** the published fine-tuned-vs-zero-shot
deltas measure *training + a prompt change*, not training. They are not
evidence that fine-tuning cannot help.

**Fix:** `experiments/finetuning/shared/eval_parity.py` renders every training
row through the evaluator's own builder, after mapping it onto the loader's
field layout (choices split out; NLI premise → context, hypothesis →
question, exactly as TRAM loads). No system message. `prompt_format:
eval_parity` in the config selects it (`data_loader.tokenize_example_parity`);
`legacy` stays the default so old arms reproduce. Evaluation of a parity arm:
`run_eval_vllm.py --system-prompt none --date-string "26 Jul 2024"`.
Tests: `tests/test_eval_parity.py` (a training row renders byte-identical to
the benchmark item's prompt; labels are exactly answer + `<|eot_id|>`).

## 2. MAJOR — the chat template stamps today's date into every prompt · FIXED

Llama-3.2's template renders `Today Date: <strftime_now>` (verified: "23 Sep
2026"). Training text and each evaluation run carried the date they were
rendered on, so arms run on different days saw different prompts — on a
*temporal* benchmark. Fix: `date_string` pinned to "26 Jul 2024" (the
template's own fallback) at training and evaluation; recorded in every
prediction row and enforced on resume (`run_eval_vllm.py`). The zero-shot
reference is re-run with the same pin (`zs-vllm-pinned`).

## 3. MAJOR — training rows whose answer was truncated out of the context · FIXED

`data_loader.tokenize_example` cuts the tail of long contexts by a 3.5
chars/token heuristic and keeps the gold as the target. On v10's train split,
432–497 TimeQA rows (the two audits' counts differ by matching rule) lost the
only occurrence of their gold. Fix: parity tokenisation truncates by tokens
and **drops** a row whose extractive gold falls in the removed part (306
TimeQA rows on v11 after decontamination); no " [truncated]" marker, which
evaluation contexts never carry.

## 4. MAJOR — the config seed reached LoRA init only · FIXED

`TrainingArguments` was built without `seed=`, so data order and dropout were
always seed 42. Fixed in `train.py`; matters for the v11 seed replicates.

## 5. MAJOR — checkpoint selection and HPO used in-distribution val loss · FIXED (for v11)

`load_best_model_at_end` on `eval_loss` picked the epoch-2 checkpoint for
v5/v6/v9-glm. The val split is the training distribution (1,090 of 1,110
AUG_GLM2 val rows share their exact passage with train), so "best" meant best
at fitting the synthetic data. The old `hyperparameter_search.py` (source of
the learning rate every arm since v2 used) optimised that same loss on a
different, older dataset, with 500 train / 200 val rows, 1 epoch and
`max_seq_length` 1024 — and its docstring claims to search batch size and
LoRA rank, which the code holds fixed. Its 4.62e-4 was then used for 3
epochs over 12k rows. v11 selects on benchmark-format dev accuracy instead
(§8, protocol doc).

## 6. MAJOR — zero-shot reference is the HF engine for TIME/TimeBench · FIXED (for v11)

`ARMS[...][0]` "zero-shot" is `zero_shot_v3` (HF); every fine-tuned arm since
v6-vllm is vLLM, and McNemar paired against the HF run. Measured gap: TIME
41.44 vs 41.39, TimeBench 45.18 vs 45.02 (McNemar b/c 90/57). Against the vLLM
zero-shot, v9-glm on TimeBench is +0.03pp, not −0.13pp. `rescore_v5_protocol.py
--reference <label>` now selects the reference; v11 uses `zs-vllm-pinned`.

## 7. MAJOR — benchmark contamination through shared passages · FIXED

Question-level checks were clean, but `build_v5`'s purge only compared
questions (Jaccard > 0.8) and whole-context token sets, so paraphrased TimeQA
questions over the same Wikipedia page as a TimeBench test item passed. 266
rows (data audit) shared a passage with 664 TimeBench items; for 298 of those
items (33% of TimeBench `timeqa`) a training row even had the identical gold
(e.g. Gene Markey's spouse, 1939–41 vs Jul–Nov 1940, both "Hedy Lamarr").
Inflates fine-tuned TimeBench by up to ~1.4pp; present in every arm since v6.

Fix: `scripts/build_v11_parity_data.py` removes any row whose context shares
a run of ≥ 30 tokens with any TIME/TimeBench/TRAM test context or question
(25-token shingles, stride 6 — guaranteed to catch every ≥30-token run), or
whose question shares one with a test context, or matches a test question
exactly. Instruction templates (question shingles recurring in ≥ 20 test
items) are not content; an earlier draft that ignored this flagged 1,016
invented AUG_GLM2 rows, every one a template hit (TIME's Timeline and
Computation instructions), and was corrected before use. Result: **561 TimeQA
rows removed (459 train, 102 val), 0 AUG_GLM2.**

## 8. MAJOR — relation/ordering rows taught answers outside TRAM's gold label space · FIXED

AUG_GLM2 `relation` golds were BEFORE/DURING/IDENTITY; on TRAM, DURING and
IDENTITY occur only as distractors (TRAM golds: BEFORE, AFTER, IS_INCLUDED,
SIMULTANEOUS, INCLUDES). 24% of `ordering` golds were "Undetermined", which
TRAM never uses as gold. These rows train the model to pick a wrong option.
Removed (124 rows). Label *frequencies* were deliberately not matched to
TRAM's test distribution — that would be fitting a prior on the test set. The
card-level cause (`MASTER_PROMPT.md` relation/ordering cards) is a generator
design error to fix before any further AUG_GLM2 generation.

## 9. MAJOR — TRAM counts NLI twice · DISCLOSED

TRAM's 564,268 NLI rows are 282,134 premise/hypothesis pairs, each once as
MCQ and once as SAQ. The micro headline is therefore NLI-weighted, and TRAM's
McNemar treats correlated duplicates as independent (overstated
significance). The metric choice decides the sign for v9-glm (−2.48pp micro,
+1.58pp macro). The micro headline stays primary for continuity with every
published number; macro is reported beside it, and significance on TRAM is
quoted with this caveat.

## 10. MAJOR — undocumented fourth variable in v10-glm · DISCLOSED

The 15,000-row cap fills TimeQA → AUG_GLM → AUG_SEQ → TLQA, so doubling
AUG_GLM2 cut TLQA 4,022 → 1,068 (−73%). Not in v10's manifest or its
confound list. v10-glm is superseded before launch (§1, §7), so this is
recorded rather than fixed; v11's `aug_fraction` knob changes composition
explicitly.

## 11. MINOR findings

- **Answer-extraction rules tuned on fine-tuned test outputs** (`run_baselines.py:388-435`,
  e.g. "+21.2pp on v4's Order_Compare") — documented as inert for zero-shot,
  so the bias favours fine-tuned arms. DISCLOSED; the scorer is frozen, not changed.
- **Letter-sequence normaliser only knows a–d** (`metrics.py:96`): "A,B,C,D,E"
  and "B,A,C,D,E" normalise alike. Inert on all benchmark items (all 11,361
  TIME sequence golds use 3 letters; 0 false credits). DISCLOSED.
- **TimeQA golds with tokenisation artefacts** ("F.A . Selangor", ~1.9%) — may
  cost exact match; left as-is because TimeBench's own timeqa golds share the
  source formatting. DISCLOSED.
- **Coverage gaps:** no training analogue for TIME Extract (multi-select, 3,340
  items), TRAM arithmetic/frequency/typical_time/causality/ambiguity (~71k),
  TimeBench tracie/date_arith. DISCLOSED.
- **MenatQA** is absent from the evaluated TimeBench — by construction: the
  loader reads the canonical `TimeBench-full-19000.zip`, which contains no
  MenatQA; only the separate 7,553-item subset folder does. Not a bug. DISCLOSED.
- `rescore_v5_protocol.py`'s "newest arm" per-category print picks from a stale
  list (display only). OPEN, cosmetic.
- `check_co_temporality` (added 2026-09-23 to `ingest_glm_batch.py`) had no
  test — added to `tests/test_glm_ingest.py`.

## Checked and fine

Label masking (3,000 sampled rows decode to exactly answer + `<|eot_id|>`);
padding (pad = eos, labels padded −100); every v10 config key is read by
train.py; merge dtype consistent with the zero-shot arm (fp16 in vLLM); the
vLLM guard against evaluating an unmerged base; greedy decoding, 128 new
tokens, 4,096-token left truncation identical across arms; scored item sets
identical across arms (TIME 104,939 / TimeBench 21,075 / TRAM 980,918); stable
per-item ids; McNemar pairing and formula; no question overlap train↔val; no
empty targets.

## What this changes

1. **Old results stand as measured, but their interpretation changes**: they
   compare zero-shot against *fine-tuning plus a prompt switch*. Say so
   wherever a delta is quoted.
2. **v10-glm is superseded before launch** (`run_schedule_v10_glm.sh` now
   refuses to run without `FORCE_V10=1`).
3. **v11** = parity prompt + decontaminated data + dev-selected
   hyperparameters: `scripts/run_schedule_v11.sh`, protocol in
   [`hpo_v11_protocol.md`](hpo_v11_protocol.md).

## Follow-up audit, 2026-09-25 (after v11's seed-42 results)

Checked whether v11's gains are real before quoting them, and whether the
remaining schedule stages would complete correctly.

**Gains are not an artifact (checked):**
- Provenance: both arms vLLM, `date_string` "26 Jul 2024", `system_prompt`
  false; the fine-tuned predictions come from the merged t09 adapter.
- Rescue rules help ZERO-SHOT, not v11: rule credit TIME 0.98 vs 0.23pp,
  TimeBench 10.95 vs 0.02, TRAM 27.49 vs 0.11. Strict first-line scoring
  widens v11's lead (+6.42 / +12.93 / +34.55). §11's "rules tuned on
  fine-tuned outputs favour fine-tuned arms" does not hold for v11.
- Abstain artifact: v11 85.4% vs zero-shot 54.4% on TIME's 2,427 abstain-
  option items ≈ 0.6pp of the TIME gain — quote no-abstain (+5.05).
- Learned abstention off-benchmark is negligible: 0.16% of TimeBench and
  0.11% of TRAM answers (abstain is never gold there).
- The final rescore (stage E) was dry-run end to end on the real files: dev
  ids excluded, `zs-vllm-pinned` as reference, seeds reported missing until
  they exist, no crash.

**Fixed:**
- §9's three-seed verdict was never computed by the schedule → new
  `scripts/summarize_v11.py`.
- The HPO's dev-only prediction files would have been flagged as "unlisted
  arms" by the rescore → `results/hpo_v11/` added to `_NOT_ARMS`.
- The rescore's per-category print always showed a stale arm (v6d) → now
  prefers v11-best (display only; the §11 cosmetic item, closed).

**Found, recorded for the next cycle (not changed — v11 is pre-registered):**
- Category regressions: TimeBench temporal_dialogue −18.45, TRAM storytelling
  −11.31, TimeBench duration −7.74, TIME Extract −2.64 (mechanisms in
  `results_and_methodology.md` §10.3). Mostly wrong-option choices, not
  format. Storytelling's likely cause is a generator-card mismatch (date-
  contradiction endings vs TRAM's commonsense plausibility).
- 56.8% of TIME prompts exceed the 2,048-token training window; ~4.9% exceed
  the 4,096-token eval window and are left-truncated (instructions and chat
  header cut). Same for both arms; a next cycle should train longer or
  truncate the context instead of the whole prompt.

## Follow-up, 2026-09-26 — silent data corruption on disk

The schedule's final rescore crashed with `KeyError: 'reference'` in
`results/tram_fixed/v1/llama/tram/finetuned/predictions.jsonl` — a file
written 2026-09-12 and never modified (mtime unchanged). It scored cleanly in
the 09-25 dry run (0 torn lines); on 09-26 it held 6 unparseable lines and 2
rows whose key read `referefce` — a single flipped bit (0x6E → 0x66). Not a
code path: storage or memory corruption. Contained so far: every recorded
sha256 (v9_glm / v10_glm / v11 training data, the dev split) re-verified
intact, and the damaged file reads consistently now. The scorer now counts a
row that has lost a required key as torn instead of crashing. **A disk/RAM
check is recommended** before trusting long-lived artifacts further.
