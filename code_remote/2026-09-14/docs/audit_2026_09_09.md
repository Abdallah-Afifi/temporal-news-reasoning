## 3. MEDIUM — reproducibility / maintenance hazards

- **M1** `run_eval_vllm.py:39-53` — `--adapter-dir` selects only the training system prompt, never LoRA weights; base model + adapter dir silently evaluates the BASE model into a `finetuned/` dir. Guarded only by schedule comments + merge stages; the runner itself checks nothing.
- **M2** `run_baselines.py:520-527` / `run_eval_vllm.py:70-78` — predictions path keyed only by results-dir/benchmark/mode: two adapters sharing a results-dir resume onto each other's predictions (silent arm mixing). Only naming convention prevents it.
- **M3** Engine protocol divergence: HF sorts prompts by length + token-budget batches; vLLM runs dataset-order chunks of 1000. Cross-engine cells rest entirely on the parity gate (94.40% llama agreement — see M4), and the rescore's "PARTIAL = length-sorted prefix" exclusion rationale (rescore:174-177) is false for vLLM legs (they're dataset-order prefixes).
- **M4** `compare_parity.py:57` gate requires ≥99% normalized agreement; llama adoption cites 94.40% (a FAIL by the coded gate), and `run_schedule_v7.sh:171-173` runs compare_parity with `|| true` — gate and decision contradict each other.
- **M5** `audit_output_style.py:127`, `eval_letter_probe.py:65-66` — tokenize with `add_special_tokens=True` after `apply_chat_template` → double-BOS, diverging from the real eval path (`src/models/inference.py:147-152` passes False deliberately; double-BOS is the documented prime Mistral-parity suspect). These probes don't measure the deployment prompt.
- **M6** `run_full_finetuned_eval.sh:22-39` — off-protocol legacy runner (batch 16 vs D47's 32, token budget 65536 vs 57344, writes into the v1 arm dir).
- **M7** `merge_lora.py:30-32` — idempotency check is "config.json exists → skip"; an interrupted merge (config written, shards incomplete) is treated as done → vLLM loads a corrupt model.
- **M8** `run_queue_v4/v5/v6/v7.sh`, `run_baseline_v3.sh` — unconditional "queue complete" markers even when legs FAIL (the D55/D56 trap `run_schedule_v7_corrected.sh` was written to fix); scripts remain launchable.
- **M9** No lockfile on any driver — double-launch interleaves appends; `rescore` counts LINES so duplicate ids would inflate `n` past expected and silently NOT be excluded.
- **M10** `run_baselines.py:503` + `metrics.py:311-336` — live-report `by_category` is all-"unknown" for TIME (reads `temporal_type`, TIME carries `Task`); stored per-row fallback + rescore table are correct — two reports disagree for the same run.
- **M11** `src/data/data_loader.py:641-674` — TRAM ids are load-scope dependent (task-filtered vs full load re-keys every id) and CSV iteration order inside task zips is unsorted (7 zips have ≥2 CSVs); a re-packed zip re-keys everything. Production chain always full-loads → internally consistent today.
- **M12** `src/training/train_lora.py` — a materially different trainer (no prompt-loss masking, `### Instruction` format, lr 2e-4, batch 4×4) whose README calls it "the project's main LoRA entry"; its shipped configs point at nonexistent data. Reproducing "from src/" silently produces a non-comparable model. The real trainer is `experiments/finetuning/LLaMA/train.py`.
- **M13** `audit_tram.py:129-181` — near-dup leakage search indexes only each row's single rarest token; pairs sharing a distinctive token that isn't the same rarest token on both sides are missed → leakage can be under-counted.
- **M14** `rescore_all.py` — stale first-gen rescorer, still runnable, with a dead-walrus completeness check (always True) and wrong expected TIME count.
